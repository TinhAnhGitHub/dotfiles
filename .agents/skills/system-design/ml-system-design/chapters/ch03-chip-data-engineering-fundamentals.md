# Chapter 3: Data Engineering Fundamentals

**Source**: Designing Machine Learning Systems — Chip Huyen, Chapter 3

## Core Idea

Production ML depends on a data layer that can collect, represent, store, retrieve, move, and process data as it grows. The right choice follows future access patterns and operational needs, not fashion. Data engineering spans raw inputs, schemas and formats, data models, storage engines, transformations, interprocess dataflow, and the distinction between historical batch data and live streams.

## Frameworks Introduced

Data sources include user input, system logs and outputs, behavioral events, internal databases, and first-, second-, and third-party data. Serialization formats can be compared by text/binary representation, readability, size, and access pattern. Relational, document, and graph models emphasize different structures. OLTP and OLAP describe transactional and analytical workloads, while ETL/ELT describe when transformation happens. Three dataflow modes are databases, request-driven services, and real-time transports; batch and stream processing then operate on the resulting data.

## Key Concepts

User input is often malformed and latency-sensitive. Logs are generally cleaner and can be processed periodically, but their volume grows quickly and needs retention and access-cost decisions. Behavioral data is still personal data even when generated by a system, and privacy constraints affect its use. JSON is flexible and readable but verbose and schema changes can be painful. Row-major formats such as CSV favor example-oriented reads and writes; column-major formats such as Parquet favor reading selected features from very wide data. Binary formats save space and can be efficient, but require compatible readers.

A data model determines which questions are easy. Relational tables support normalization and declarative SQL, but normalization can make joins expensive. Document models keep self-contained records and tolerate different schemas, but cross-document queries and joins are harder. Graph models explicitly represent nodes and relationships, making multi-hop relationship queries natural. “Schemaless” documents do not remove structure; they shift the responsibility for assumptions from writers to readers. A data warehouse generally stores processed structured data, while a data lake stores flexible raw data; lakehouse systems combine aspects of both.

Transactional systems prioritize low latency, availability, and reliable updates; analytical systems aggregate across many rows and columns. Storage and compute are increasingly decoupled, allowing one stored representation to serve multiple processing engines. ETL extracts and validates from sources, transforms by joining, cleaning, standardizing, deduplicating, aggregating, or deriving features, then loads to a destination. ELT loads raw data first and transforms later, accelerating arrival but making later search and processing harder at scale.

Data can pass through a shared database, but shared access and database latency limit that approach. Services use REST or RPC requests and support independent components, yet synchronous dependencies can cascade failures. A broker or event bus reduces the web of dependencies. Pub/sub lets producers publish topics and consumers subscribe; message queues target intended consumers. Kafka and Kinesis exemplify pub/sub; RabbitMQ exemplifies queues.

## Mental Models

Choose representation by how data will be read, written, joined, and retained. Make schema responsibility explicit. Separate durable historical storage from low-latency transport, and separate data movement from computation. For ML, static batch features and dynamic streaming features often must be joined.

## Anti-patterns

- Choosing a format without considering access patterns.
- Treating unstructured data as structure-free or privacy-free.
- Forcing every workload into one data model or database.
- Building a synchronous dependency web among services.
- Recomputing long windows unnecessarily when stateful streaming can update state.
- Storing raw data without a plan for validation, transformation, retrieval, or retention.

## Worked Example

In ride sharing, driver availability and ride demand change quickly. A driver-management service and ride-management service can publish predictions to a real-time transport; a price-optimization service consumes the latest values. Slowly changing driver ratings can be batch features, while current availability and recent demand are streaming features. Durable storage retains events for later analytical and training jobs.

## Key Takeaways

Understand where data originates and what guarantees it needs. Match formats and models to access patterns. Validate early in ETL, preserve lineage, and make privacy part of design. Use asynchronous transports when many services share changing data. Combine batch and stream processing when prediction needs both stable history and current state.
